# 质量改进记录（报告质量）

> 目的：把"报告质量"从**凭感觉**变成**可测量、可回归**的工程对象。
> 维护规则：每次改提示词 / 换模型 / 改评分权重，**追加一节**并附实测数据，不改历史结论。

| 项 | 内容 |
|---|---|
| 适用对象 | 报告生成链路：`server/llm/prompt.js` → `server/llm/llm.js` → `server/scoring/` → 前端 `ReportView` / `ObjectiveCard` |
| 观测数据来源 | 本地库 `server/data/app.db` 的 `evaluations`（报告全文 + `objective_json`）与 `llm_usage`（模型 / token） |
| 当前基线日期 | 2026-10-09 |

---

## 1. 验收指标（每次改动后必须过这四条）

| # | 指标 | 判定标准 | 观测方式 |
|---|---|---|---|
| 1 | **编造** | 报告（尤其【逐条改法】的"改之后"）不得出现简历里没有的事实与数字 | 人工核对 + 数字白名单比对（排除评分刻度、日期格式差异、`〔待补〕`内示例） |
| 2 | **格式完整** | 9 个小节齐全，且小节名**逐字**与契约一致（含「可继续增强的方向」） | 正则统计 `【】` 小节 |
| 3 | **标记自洽** | 【岗位匹配对照】给 ✅ 的行，理由里不得出现"未提及 / 未体现 / 证据不足 / 证据偏弱" | 逐行检查标记与第三段 |
| 4 | **可执行** | 每条改法有"改之前→改之后"、标注命中 JD 第几条、缺数据用 `〔待补：…〕` | 统计"命中 JD"标注数与占位符数 |

**已知的指标误报**（比对时须排除）：
- `10`：来自「X / 10 分」的评分刻度；
- 日期类：模型会把 `2020年7月` 规范成 `2020.07`，需归一化后比对，否则误判为编造；
- `50`／`P99`：目标值（如"Star 50+"）与百分位名，不是事实断言；
- `〔待补：…〕` 内的举例文字不算断言。

## 5. r2 迭代（2026-10-09 下午）

### B1 评分稳定性——实测结论：**总分稳定，逐条判定有波动**

同一份简历 + 同一份 JD（取真实测试 #20 的输入）连跑 3 次（`temperature=0.1`）：

| 维度 | 三次结果 | 波动 |
|---|---|---|
| **总分** | 7 / 7 / 7 | **极差 0** ✓ |
| 结论方向 | 三次一致（"可以投，短板是通信/音视频"） | 稳定 ✓ |
| ✅ 行数 | 6 / 8 / 9 | 波动 3 行 |
| 报告口径匹配度 | 71% / 83% / 88% | 17 个百分点 |
| 报告字数 | 5309 / 4557 / 4889 | ±750 字 |
| 耗时 | 60.8s / 55.2s / 55.0s | — |

**决策：不追加 prompt 改动。** 总分（用户主要依凭的指标）零波动、短板判断稳定；逐条 ✅/⚠️ 的差异属模型主观判定范围，继续加压的边际收益低且有回归风险。同时注意：算法侧的 `matchScore` 是确定性的，两次同样输入的"岗位匹配度"不会变——用户看到的稳定数字是它。

**使用建议（写给使用者自己）**：比较两次评估时，看**总分与短板清单**，不要逐条对比 ✅ 的数量。

### B5 旧记录回填——已实现（迁移 v15）

问题：拆分上线（2026-10-09）前落库的 16 条记录，`objective_json` 里没有 `qualityScore`，结果页只能拿旧的**综合分**顶在「简历质量」徽标上——那个数字被岗位匹配度拉着走，正是这次要拆开的语义。

实现要点：

- 重算逻辑只有一份：`scoring/evaluate.js` 的 `backfillObjectiveScores(objective)`，**当场评分与历史回填共用**，因此回填值 ≡ 该记录今天重新算一遍（权重常量不会两处漂移）
- 迁移 **v15** 只做「读 `objective_json` → 补字段 → 写回」，**不调模型、不重新解析简历**：`qualityScore` 由已存的 `dimensions` 重算（质量分与岗位无关，故结果与当时一致），`matchScore = round2(matchRate × 100)`；无需改动时返回 `null`、跳过写库（幂等）
- 回填只**新增字段**，`score` / `dimensions` / `matchRate` 原样保留，旧快照与分享页仍可解析；`JSON.parse` 失败的脏数据跳过、不阻塞启动
- 测试：`scoring.test.js` 新增「历史回填」与「回填后质量分 ≠ 旧综合分」两例；`migrations.test.js` 新增端到端用例（插老结构记录 → `user_version` 退回 14 → `migrate()` → 断言与重新评分逐字段一致）

真实库执行结果（`server/data/app.db`，执行前已用 `VACUUM INTO` 快照到 `backups/app-2026-10-09-before-v15.db`）：

| 项 | 结果 |
|---|---|
| 版本 | 14 → **15** |
| 缺 `qualityScore` | 16 条 → **0 条** |
| 缺 `matchScore`（有 `matchRate` 的） | 14 条 → **0 条** |
| 已有新字段的记录（#20/#21） | **未被改写**（幂等已验） |
| 无 `objective` 的记录（#4 脏数据、#12 面试） | 跳过，行为不变 |

回填前后的可见差异（都是真实记录，徽标上的数字因此变了）：

| 记录 | 旧显示（综合分当质量分） | 现在：简历质量 | 现在：岗位匹配度 | 说明 |
|---|---|---|---|---|
| #6 | 37.51 | **20.43** | 77.36% | 简历写得差但很对口 → 旧口径被匹配度**虚高** |
| #15 | 76.05 | **88.57** | 46.84% | 简历写得好但不太对口 → 旧口径被匹配度**拉低** |
| #19 | 53.68 | **70.23** | 15.08% | 同理，旧口径把"对口度"混进了"质量" |

两种偏差方向都出现了——旧口径把"简历写得好不好"与"跟岗位配不配"混成一个数，正是这次修正的问题。
