# 04 数据库版本化迁移：PRAGMA user_version 顺序回放

**优先级**：P2　**预估**：半小时　**前置依赖**：无

## 现状

`server/core/db.js` 的表结构变更是散落的守卫式 ALTER：

```js
// :114-118
if (!columns.includes("job_title")) db.exec("ALTER TABLE jd_keywords ADD COLUMN job_title TEXT DEFAULT ''");
// :195-201
if (!columns.includes("person_key")) db.exec("ALTER TABLE evaluations ADD COLUMN person_key TEXT");
// ...共约 10 处，分布在文件各处
```

问题：每加一列都要人肉保证幂等与顺序；无法表达数据回填类迁移；新开发者不知道
"改表要在哪里加什么"。`PRAGMA user_version` 目前未使用。

## 目标

所有 DDL 收进一个编号迁移数组，启动时按 `user_version` 顺序回放，只执行未执行的。

## 实现步骤

### 1. db.js 内新增 migrate 区块（保持单文件也可以，或抽到 `server/core/migrations.js`）

```js
const MIGRATIONS = [
  { v: 1, up: () => db.exec(`CREATE TABLE IF NOT EXISTS users (...)` /* 现有建表语句 */ ) },
  { v: 2, up: () => db.exec(`CREATE TABLE IF NOT EXISTS evaluations (...)`) },
  // ...把现有全部 CREATE TABLE / CREATE INDEX 按当前文件顺序编号
  // 守卫式 ALTER 也编进去，保留原有的 if (!columns.includes(...)) 守卫（对老库幂等）：
  { v: 10, up: () => { if (!columnExists("jd_keywords", "job_title")) db.exec("ALTER TABLE ..."); } },
];

function migrate() {
  const current = db.pragma("user_version", { simple: true });
  for (const m of MIGRATIONS) {
    if (m.v <= current) continue;
    db.transaction(() => { m.up(); db.pragma(`user_version = ${m.v}`, { simple: true }); })();
  }
}
migrate();
```

### 2. 关键决策：老库兼容

已有生产库（含全部列）跑新 migrate 时，前面的守卫式语句全部跳过、CREATE IF NOT EXISTS
无副作用 → user_version 从 0 一次性推进到最新。**不需要**写"探测当前版本"的复杂逻辑。
在 migrate() 上方用注释说明这一点。

### 3. 加一条防呆测试 `server/__tests__/migrations.test.js`

- 用 `:memory:` 新库跑 migrate → `user_version === MIGRATIONS.length`，关键表存在；
- 跑两遍 migrate → 幂等，不抛错，版本不变。

### 4. 文件头加使用说明注释

```js
// 改表结构的唯一方式：往 MIGRATIONS 数组【尾部】追加 { v: 上一个 v + 1, up: ... }。
// 不要修改历史迁移的内容（已上线的库不会重放）。
```

## 验收标准

- [ ] `grep -c "ALTER TABLE" server/core/db.js` 的所有命中都位于 MIGRATIONS 数组内
- [ ] 删除 dev.db 启动服务 → 正常建库，`PRAGMA user_version` = MIGRATIONS.length
- [ ] 用已有数据的旧库（改造前备份一份）启动 → 数据完好，版本推进
- [ ] `npm test` 全绿（含 migrations.test.js）；`npm run acceptance` 17/17

## 注意事项

- `db.pragma("user_version", { simple: true })` 是 better-sqlite3 的正确写法，不要用
  `db.exec("PRAGMA user_version = N")` 以外的技巧。
- 迁移必须同步执行（better-sqlite3 本身同步），不要引入 async。
- `server/jobs/purge.js` 的 `tablesWithUserId()` 依赖 PRAGMA table_info 动态发现，
  不受本次改造影响，确认测试 `97b9b14` 引入的防呆测试仍通过。
