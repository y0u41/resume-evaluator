# 01 额度计费统一：withQuota 唯一入口 + 失败自动退还

**优先级**：P1（商用前必须）　**预估**：半天　**前置依赖**：无

## 背景与现状

同一个"消耗用户额度"行为，目前四条路径有四种不一致的实现，全部在 `server/routes/evaluate.js`：

| 路由 | 扣费位置 | 问题 |
|---|---|---|
| `POST /evaluate`（:235） | `acquire` 排队**之后**、LLM 调用**之前** | LLM 失败时额度照扣，无退还 |
| `POST /compare`（:465） | 每个 job 的 LLM 调用**成功之后** | `consumeQuota` 返回值被丢弃，仅靠 :425 的预检查 `used + jobs.length > limit` 把关；预检查与逐 job 计数之间存在并发竞态，理论上可小幅超额 |
| `POST /interview`（:620） | `acquire` 排队**之前** | 排队失败（503"排队人数过多"）时额度已扣，白扣 |
| `POST /directions`（:726） | `acquire` 排队**之前** | 同上 |
| `POST /followup`（:502 起） | **完全不计费** | 每次携带全文简历+完整报告的 LLM 调用，免费用户可无限刷 |

注册用户没有任何退款机制；游客路径有 `refundGuestQuota`（`server/routes/guest.js:47`），
模式可参考但实现独立。

额度读写在 `server/core/quota.js`：
- `consumeQuota(user, { isPremium, isOcr })` → 检查并 `incr`，返回 `{ allowed, reason?, used, limit, ... }`
- 计数表 `quota_counters(user_id, day, kind)`，kind ∈ total / premium / ocr
- 超额提示 `quotaMessage(quota)`；业务错误码 3001（见 `evaluate.js:242`）

## 目标

1. 路由层不再直接调用 `consumeQuota`，只调用 `server/core/quota.js` 新增的 `withQuota`。
2. **成功后计费 + 失败自动退还**成为唯一定价策略（记入 ADR-0008）。
3. followup 纳入计费；interview/directions 的扣费顺序 bug 随重构自然消失。

## 实现步骤

### 1. quota.js 新增两个函数

```js
// 计费唯一入口：work() 成功 → 计费；work() 抛错 → 不计费（或退还已扣额度）。
// 返回 work() 的结果；额度不足时抛出 code=3001 的错误（路由层按现有 429/流式 error 事件处理）。
export async function withQuota(user, { isPremium = false, isOcr = false } = {}, work) {
  const quota = consumeQuota(user, { isPremium, isOcr });
  if (!quota.allowed) {
    const err = new Error(quotaMessage(quota));
    err.code = 3001;
    err.quota = quota;
    throw err;
  }
  try {
    const result = await work();
    return { ...result, quota };        // 路由可能需要 quota 做响应头/日志
  } catch (error) {
    refundQuota(user.id, { isPremium, isOcr });
    throw error;
  }
}

// 退还一次额度（MAX(count-1, 0) 防止负数），模式与 guest.js 的 refundGuestQuota 一致
export function refundQuota(userId, { isPremium = false, isOcr = false } = {}) {
  const kinds = ["total", ...(isPremium ? ["premium"] : []), ...(isOcr ? ["ocr"] : [])];
  for (const kind of kinds) {
    db.prepare(
      "UPDATE quota_counters SET count = MAX(count - 1, 0) WHERE user_id = ? AND day = ? AND kind = ?"
    ).run(userId, today(), kind);
  }
}
```

注意：上面是"先扣后退"实现（简单、和现状改动最小）。等价做法是 `work()` 成功后再
`consumeQuota`（compare 已是此模式）——两种都接受，但**必须二选一全局统一**，并把
选择理由写进 `docs/adr/0008-quota-charged-on-success.md`（新建，格式对齐 ADR-0007）。

### 2. 四个路由改造（evaluate.js）

以 `/evaluate` 非流式分支为例（流式分支同理，把 `callLLM` 到 `saveEvaluation` 整段包进 work）：

```js
// 原来：line 235 consumeQuota + 后续裸调用
// 改为：在 acquire 拿到槽位之后
const { result: report } = await withQuota(req.user, { isPremium: isPremiumModel(effectiveModel(override)) }, async () => {
  const report = await callLLM(resume, jobTitle, jobDescription || "", controller.signal, override);
  // saveEvaluation 也放进 work 里：落库成功才算这次"成功"
  const score = extractScore(report);
  const id = saveEvaluation(...);
  maybeLogFirstEvaluate(req.user.id);
  return { report, id };
});
```

- `/interview`、`/directions`：删掉 acquire 之前的 `consumeQuota`（:620、:726），
  LLM 调用段包进 `withQuota`。
- `/compare`：循环体里每个 job 包一次 `withQuota`（替代 ：465 的裸调用）；
  :425 的整包预检查**保留**（给用户"额度不够跑不了 N 个"的提前反馈，体验更好），
  预检查逻辑可抽成 `hasQuotaFor(user, n)` 放进 quota.js。
- `/followup`：LLM 调用段包进 `withQuota`（isPremium 按 override 判断）。
  这是行为变更：追问开始消耗每日总额度——在 commit message 和
  `docs/features/评估简历.md` 里明确写出。

### 3. 退款语义（写进代码注释）

- `work()` 抛错即退（含流式中途失败：用户看到了部分文本但没有落库记录，退是公平的）。
- 客户端主动断开（`controller.signal.aborted`）**不退**——服务端会继续跑完并落库
  （这是 evaluate.js:197 的既有决策），用户能在历史里拿到结果。

### 4. 新增单测 `server/__tests__/refund.test.js`

- LLM work 抛错 → `quota_counters` 计数不变；
- 成功 → total +1，isPremium 时 premium +1；
- 连续失败 3 次 → 计数仍不变（MAX 防负数）；
- 复用现有测试里 mock LLM / 内存库的方式（参考 `server/__tests__/` 现有写法）。

## 注意事项

- 流式路径里 `withQuota` 的 work 是长时间运行的流回调，注意不要把 `safeWrite` 放进
  work 外层（断连时 safeWrite 必须仍可用）。
- `/evaluate` 的缓存命中分支（evaluate.js:172-195）在 acquire 之前直接返回，**不计费**，
  保持现状不要动。
- admin 用户 `isUnlimited` 不计数，withQuota 天然兼容（consumeQuota 已处理），不要加特判。
