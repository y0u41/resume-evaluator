# 07 文档与管理员体验：规模触发器表 + 超时申请高亮

**优先级**：P3　**预估**：半小时　**前置依赖**：无

## 任务 A：Tech_Design 写入"规模触发器"表（15 分钟）

### 现状

`docs/Tech_Design.md` 把 SQLite / 内存队列 / 单实例列为"已知限制"，但没有回答
"**什么时候必须换**"。临场拍脑袋是架构决策最差的方式。

### 实现

在 `docs/Tech_Design.md` 的限制章节前插入：

```markdown
## 规模触发器（出现任一信号即启动迁移，在此之前不要提前优化）

| 组件 | 触发信号（任一） | 迁移方向 | 预估工作量 |
|---|---|---|---|
| SQLite (WAL) | 日评估 > 500 次/天；或需要部署第二个实例 | Postgres（表结构基本通用，改连接层与 SQL 方言） | 2-3 天 |
| 内存并发队列 (MAX_CONCURRENCY=5, MAX_QUEUE=50) | 部署第二实例；或排队等待成为常态（waiting > 10 分钟均值） | Redis + BullMQ | 2 天 |
| 游客 IP 限流 / A/B IP 分桶 | 部署第二实例 | Redis 计数器（分桶改用 userId 或 Cookie） | 1 天 |
| events/llm_usage 聚合查询变慢 | admin 页加载 > 2s | 预聚合日表（SQLite 内即可做，不必换库） | 半天 |
```

并注明：**这些数字是拍脑袋的保守值，第一次真实接近时先实测再决定。**

## 任务 B：管理员 PRO 申请超时高亮（15 分钟）

### 现状

`src/pages/Admin.tsx` 的 PRO 申请卡片列出申请（`pro_requests` 表，含 created_at），
但无时间紧迫性提示。人工对账最大的失败模式是**漏单**——用户付了款、填了邮箱、
管理员没看到，等 24 小时无回应的付费用户基本流失且会差评传播。

### 实现

1. `src/pages/Admin.tsx` 申请列表项：`created_at` 距今 > 24h 且状态仍为 pending →
   加琥珀色左边框或 "⚠ 超过 24 小时未处理" 徽章（对齐现有 Tailwind/样式写法，
   参考卡片内已有的"样本量不足"警告样式）。
2. 顶部统计行加一个计数："N 条申请超过 24 小时未处理"（N>0 时显示）。
3. 不需要后端改动：前端拿现有列表按 created_at 计算即可。若列表接口未返回
   created_at，在 `server/routes/admin.js` 的申请列表查询里补该字段。

### 验收

- [ ] 造一条 2 天前的 pending 申请（直接改 dev.db 或插入测试数据）→ 管理后台出现高亮与计数
- [ ] 批准/拒绝后高亮消失
